# v1.0 Release Candidate Checklist

This checklist tracks the conditions that must hold before a v1.0 Release
Candidate is prepared. It is a preparation aid only.

**The checklist itself is not acceptance.** Ticking every box records that the
listed conditions were observed; it does not accept the Project, authorize a
commit, create a tag, publish a release, or deploy anything. Acceptance,
release readiness, release, and deployment remain distinct decisions under
[`docs/project-closure-and-final-delivery.md`](../project-closure-and-final-delivery.md).
Every gate below is satisfied by referenced evidence, not by the tick itself.

## Gates

- [ ] `validate.py` passes
- [ ] full regression passes
- [ ] Phase 11 independent review completed
- [ ] at least one Host Acceptance Record completed
- [ ] candidate hosts explicitly marked verified/unverified
- [ ] no unresolved Major/Critical Finding
- [ ] CHANGELOG contains candidate version section

## Gate Evidence

Record the observed evidence for each gate before ticking it. A gate whose
evidence is missing stays unticked; it is not carried as an assumption.

| Gate | Required evidence | Observed status |
|---|---|---|
| `validate.py` passes | command, exit code, and Git boundary of the run | observed at the Phase 11-A working boundary, not at a Release Candidate boundary |
| Full regression passes | command, test count, result, and environment | observed at the Phase 11-A working boundary, not at a Release Candidate boundary |
| Phase 11 independent review completed | review record whose reviewer did not author the change | no review record exists in this repository |
| At least one Host Acceptance Record completed | a record under `evaluations/` outside `templates/` with an `accepted` or `accepted-with-residuals` verdict for the reference host | none exists |
| Candidate hosts marked verified/unverified | the README limitations list naming every candidate host's current verdict | recorded; every candidate host is listed unverified |
| No unresolved Major/Critical Finding | Finding disposition showing no open major or critical Finding against the frozen protocol | no Finding instance store exists to check |
| CHANGELOG candidate version section | a CHANGELOG section naming the candidate version | none exists |

## Phase 11-A Review Findings

Recorded from the Spec, Standards, and Evidence reviews of the Phase 11-A
governance change. They are recorded here rather than silently fixed. None is a
Product Finding, and none creates a Ledger or a new lifecycle store.

| ID | Review | Severity | Finding |
|---|---|---|---|
| P11A-1 | Spec | minor | Making the single-authority rule machine-enforced tightens validation: a supporting `.looppilot/` artifact naming a canonical assertion outside a declared section now fails where it previously passed. Intended, but it is a behavior change for existing repositories. Migration guidance is in [`docs/v1-migration.md`](../v1-migration.md). |
| P11A-2 | Standards | minor | Derived status is declared by the `## Lifecycle Projections` heading, not by a per-row column, so "explicitly identify generated/derived status" holds at section granularity only. A per-row flag was not added because it would change a validated table schema inside the feature freeze. |
| P11A-3 | Standards | minor | The undeclared-copy check covers `.looppilot/` supporting artifacts only. A lifecycle value copied into `docs/`, `README.md`, or an evaluation file is not checked. Deliberate, since those are not lifecycle state, but the rule is not repository-wide. |
| P11A-4 | Evidence | major | The evaluation-template fields added for Scenario ID, evidence links, reviewer decision, and unverified limitations, and the record's Scenario IDs and Unverified limitations fields, are **not machine-checked**. A real Host Acceptance Record can omit them and still pass validation. Enforcement is deferred; see the RC blocker below. |
| P11A-5 | Evidence | minor | The "no unresolved Major/Critical Finding" gate has no evidence source in this repository, which holds no Finding instance store. The gate must be evidenced by the review that closes Phase 11, not inferred from absence. |
| P11A-6 | Evidence | minor | `tests/scenarios.md` scenarios are numbered headings with no stable IDs, so a recorded Scenario ID references a position that renumbering would silently break. Assigning stable IDs was out of scope for a governance-only change. |

P11A-4 is the one Finding that must be resolved or consciously accepted before
the Release Candidate: until the added disclosure fields are enforced, the
"Host Acceptance Record completed" gate can be met by a record that omits them.

## Scope Under Feature Freeze

Work discovered while closing these gates is limited to bug, compatibility,
security, documentation, host-adapter, trigger-tuning, and validator-correctness
fixes, per [`docs/cross-host-acceptance.md`](../cross-host-acceptance.md). A
failing gate MUST NOT be resolved by adding a role, mode, Ledger, lifecycle
subsystem, Barrier, or acceptance layer, and MUST NOT be resolved by relaxing
the gate.

Release Candidate preparation is not a release, not a deployment, and not user
acknowledgement.
