## 2. Distribution-004 Frozen Contract

This is the distribution contract as implemented, not as proposed. It is frozen
at `9b2e31a` plus the evidence correction recorded in section 6.

### Synchronization states

Exactly five, and no more:

```text
CURRENT · UPDATE_AVAILABLE · LOCAL_MODIFICATIONS · CONFLICT · RECOVERY_REQUIRED
```

Precedence, verified identical in both implementations:

```text
RECOVERY_REQUIRED > CONFLICT > UPDATE_AVAILABLE > LOCAL_MODIFICATIONS > CURRENT
```

The implemented token is `LOCAL_MODIFICATIONS`. `LOCAL_MODIFIED` appears nowhere
in the repository. The two names denote the same state; the implemented spelling
governs, and it was not renamed, because renaming a state purely for wording is
out of scope.

### Comparison

Per path over the union of the manifest entries and the recorded state entries:

```text
BASE   = upstream content recorded at the previous successful installation
LOCAL  = the installed file
REMOTE = the source repository file
```

| Condition | Classification |
|---|---|
| `LOCAL == REMOTE` | current, whatever `BASE` holds |
| managed, absent locally, `BASE` known | update, restoring the missing file |
| managed, absent locally, no `BASE` | add |
| `LOCAL == BASE`, `REMOTE != BASE` | update |
| `LOCAL != BASE`, `REMOTE == BASE` | local modification, preserved |
| `LOCAL != BASE`, `REMOTE != BASE` | conflict |
| no `BASE` and `LOCAL != REMOTE` | conflict |
| retired from manifest, `LOCAL == BASE` | remove |
| retired from manifest, `LOCAL != BASE` | remove-preserve |

An absent or unknown `BASE` always resolves toward conflict, never toward
overwriting local content.

### State schema

`.looppilot-installation` format `2`:

```text
FORMAT|2
VERSION|<token>
COMMIT|<40 hex>
MANIFEST|<64 hex>
FILE|<path>|<installed hash>|<customized 0|1>|<baseline hash or ->
```

Format `1` remains readable. An uncustomized format `1` row keeps its recorded
hash as `BASE`; a customized format `1` row has no recoverable baseline and its
`BASE` is unknown. Updating rewrites the state as format `2`.

Format `1` could not carry this contract: its `FILE` row stored the hash of the
file as installed, so the first preserving update overwrote the baseline with
local content and permanently destroyed the ability to separate a user
customization from a conflict.

### Transaction and recovery

Order, verified by reading both implementations:

```text
preflight → compare → detect conflicts → backup → apply → verify hashes
          → write state → complete transaction
```

Conflict refusal occurs before the journal is opened and before any backup,
copy, or delete. `.looppilot-transaction` records the backup identifier and each
intended action before that action runs, and is removed only after the state is
written and every managed file is verified against its expected hash. A residual
journal makes `status` report `RECOVERY_REQUIRED`; the next `update` or
`uninstall` rolls back from the recorded backup, clears the journal, and then
proceeds.

### Uninstall

Only paths recorded in the installation state are considered. A file is removed
only when its customization flag is clear and its current hash still matches the
recorded installed hash. Everything else is preserved and reported. The state
file is removed last. Unmanaged files are never considered for removal.

### Contract agreement

| Surface | Agrees |
|---|---|
| `distribution/loop-pilot.ps1` | yes |
| `distribution/loop-pilot.sh` | yes |
| `docs/installation.md` | yes |
| `INSTALLATION-VALIDATION.md` | yes |
| `tests/test_distribution.py` | yes |

All five use the same five state tokens, the same precedence, and the same
three-way semantics. Every Distribution-004 scenario executes on both shells as
a `subTest` per shell, so a divergence fails the suite rather than passing
unnoticed.

### Superseded behavior, retained deliberately

Distribution-001 preserved a managed file modified both locally and upstream
**silently, and reported the update as successful**. A newly managed path
colliding with different pre-existing user content was handled the same way.

Distribution-004 replaces that with the stricter conflict contract: the update
stops before changing any managed file, names every conflicting path, and exits
non-zero. `-Force` and `--force` still back up local content and take the source
version.

The two contracts are incompatible. Two regression tests encoded the old one and
were rewritten to assert refusal followed by forced resolution. This is a
deliberate replacement, and the old behavior is recorded rather than erased.

### CHANGELOG decision

`CHANGELOG.md` is **not modified**, and Distribution-004 gets no changelog entry
in this audit. The reason is specific rather than general: `CHANGELOG.md` already
carries uncommitted Phase 12 edits in the working tree. Adding a Distribution-004
entry would force one of two bad outcomes — committing the Phase 12 hunks under
an RC-audit commit, which contaminates the Phase 12 evidence boundary, or staging
a partial hunk of a file whose remaining changes stay uncommitted, which leaves
the file in a state neither partition owns.

The repository convention also has no Distribution-00N changelog precedent: no
`Distribution-00` string appears anywhere in `CHANGELOG.md`. Distribution
evidence lives in `INSTALLATION-VALIDATION.md`, which is where Distribution-004
is in fact recorded.

Gate 7 remains UNSATISFIED regardless, because it requires a candidate version
section, which is a separate authorized decision.

## 10. Exact Minimum Path to RC

Only what is required, in the order that makes each step evidenceable:

1. **Preserve a Phase 11 independent review record** in this repository, authored
   by someone who did not author the Phase 11 change. Closes gate 3, and supplies
   the Finding disposition that gate 6 has nothing to read without.
2. **Pin one host version and one model** for the whole acceptance run, and do
   not let the CLI self-update mid-session. Version drift already split one run
   across 2.1.224 and 2.1.226.
3. **Run one Lightweight-shaped and one Full-Loop-shaped fixture** from
   `tests/scenarios.md` with the Skill loaded, preserving environment, prompt,
   trace, and score for each.
4. **Run at least one fixture that activates the Skill without explicit
   invocation**, so dimension 1's activation half has evidence and can rise above
   `partial`.
5. **Have an evaluator who is not the trace author score both traces** against
   the rubric, and record the lowest critical score.
6. **Write one Host Acceptance Record** under `evaluations/` for that exact
   combination, letting its verdict follow the dimension results. Closes gate 4
   only if every dimension is `pass` or `partial`.
7. **Decide the candidate version** and add its CHANGELOG section. Closes gate 7.
8. **Re-run `validate.py` and the full suite at the chosen RC boundary** and
   record the commit. Re-closes gates 1 and 2 at that boundary.

Steps 3 through 5 are the work no phase has yet done. They cannot be satisfied by
distribution evidence, discovery evidence, loading evidence, or static validation,
however complete those become.
